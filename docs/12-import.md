# The Excel import

Most families arrive in one spreadsheet, typed during a barangay survey rather
than in this application. Treat the import as a review and correction step,
not as an unchecked data transfer. You can see what the server will save before
any family record is written.

## Workbook versions and Excel preflight

You can upload an existing Ver3 workbook. Ver3 remains a supported input so you
do not have to rewrite a completed survey just because the download changed.
New template downloads are Ver4, generated by
`app/Libraries/FamilyExcelTemplate.php`.

Ver4 includes a `CHECK` column as a convenience preflight. Red results cover
identity and household-structure Must fix cases, such as `Missing QR` and
`Multiple Heads (Same Family)`. Yellow `Card Readiness` results mean the Head
is missing Sex, Birthday, Contact Number, Address, or Barangay. They warn that
the family cannot receive an access card yet, but they do not prevent import.

This guidance is deliberately non-authoritative. The importer never reads
`CHECK` and never treats `OK` as permission to import. Excel cannot check
current QR ownership or current sector and service reference data, so the server
validates every workbook again when you upload it. In the template, `*` marks an
identity field that must be supplied and `†` marks a Head-only card field. The
examples and `app/Libraries/FamilyExcelTemplate.php` explain the distinction.

## The flow

1. Download the Ver4 template for new work, or keep using an existing Ver3
   workbook.
2. Upload the `.xlsx`. The server queues a `family_import` job, parses the
   `Families` sheet, and stages the review. Nothing is saved yet.
3. Review the exact row, cell, label, and outcome. Use the row editor and Apply
   to correct staged values. The staged review is what the server revalidates.
4. Resolve every active Must fix issue. Confirm import stays disabled until no
   active Must fix issue remains.
5. Press Confirm import. Only then are active, buildable rows written.

The background worker handles parsing because a large workbook should not make
your browser request wait. Staged rows and their review state live in
`app/Libraries/ImportStagingStore.php`; the importer and review query are in
`app/Libraries/FamilyExcelImporter.php` and
`app/Libraries/ImportReviewPresenter.php`. Confirm uses the same
`FamilyRecordWriter` path as other family writes, so it does not create a
separate kind of family record.

## What you see in review

The server stages the canonical value that it will validate and store. This
prevents a review that shows `Maria  Santos` while the saved record says
`MARIA SANTOS`.

- Names, addresses, barangays, relationships, and the other staged choice or
  free-text values use uppercase with redundant whitespace collapsed. `Maria  Santos` becomes
  `MARIA SANTOS`, and `Purok  1,` becomes `PUROK 1,`.
- Address punctuation remains meaningful. `PUROK 1` and `PUROK 1,` are still
  different addresses, so you must decide whether one needs correction.
- Suffixes use the database enum spelling. For example, `Jr.` becomes `JR`.
- QR numbers and birthdays keep their specialized parsing rules rather than
  being guessed from ordinary text.

Sector and service cells are comma-delimited code lists only. The review strips
whitespace from each token: `SC, IW` becomes `SC,IW` and `EDA 8, EDA9` becomes
`EDA8,EDA9`. Whitespace is not a separator. For example, `EDA8 EDA9` becomes the
one token `EDA8EDA9`, which you must repair by adding the comma.

After comma-only parsing and canonicalization, every unknown sector or service
token blocks import. `EDA123,EDA8` raises `Invalid Service Code` for `EDA123`
and blocks the row until you correct the cell. The server does not import
`EDA8` as a partial result. Likewise, an unknown sector blocks the row. It is
not filed under Other Sectors. `OTHER` is valid only when it is itself a listed
sector code.

## Must fix and import-allowed follow-up

The review uses **Must fix** for a condition that cannot safely be written or
would make the family ambiguous. It uses an import-allowed follow-up notice
when the database can accurately preserve that missing value and staff can
collect it later.

| Review outcome | What you must do or what will happen |
|---|---|
| **Must fix**: unreadable or empty workbook | Upload a valid workbook with the required sheet and headers. |
| **Must fix**: missing, malformed, zero, formula, error-cell, too-large, or already-assigned QR | Enter the family's actual unused QR. An assigned QR belonging to another head is not safe to reuse. |
| **Must fix**: missing FirstName or LastName | Fill in the named identity field. |
| **Must fix**: no Head or `Multiple Heads (Same Family)` | Correct the relationship so one household has one Head. |
| **Must fix**: `Duplicate QR (Multiple Families)` | Correct the other household's QR. This is not a duplicate-row decision. |
| **Must fix**: `Duplicate Row` | Keep one complete row and discard the copies from this import. |
| **Must fix**: `Invalid Sector Code` or `Invalid Service Code` | Correct the comma-delimited list to listed codes. No unknown token is skipped or remapped. |
| **Must fix**: a value exceeds a database limit | Shorten the named value so it can be stored without truncation. |
| **Warning**: blank Head Sex, Birthday, Contact Number, Address, or Barangay | The family imports without the missing value and appears in Card Readiness. A missing member value does not affect Card Readiness. |
| **Must fix, then Warning when cleared**: supplied malformed Head sex, birthday, contact number, or barangay | Correct the value, or clear it if it is unknown. Clearing removes malformed text and leaves the Head in Card Readiness. |
| **Defaulted quietly**: blank Monthly Income, Civil Status, Education, Job, or Religion | Monthly Income stores as `0.00`; the other profile fields store as `NOT PROVIDED`. No review issue is added. |
| **Import allowed, informational**: a re-upload or existing-person notice | The review names the safe result, such as a family being skipped or a member being added. Check it before Confirm. |

A blank relationship on a non-Head row imports as `MEMBER`. A blank sector or
service creates no assignment rows, which is different from inventing a generic
sector or service. The importer uses only exact listed codes, with no fuzzy
aliases. `OTHER` is valid only when it is a real listed sector code; there is no
generic Other service.

The Head is the household source for Address and Barangay. The importer ignores
both cells on member rows, including values that disagree with the Head. A blank
Head address or barangay is a Card Readiness warning, not a multiple-address
conflict.

Card Readiness is the Head-only follow-up queue at `records/completeness`. You
can filter it by barangay or missing card field, open the family record to
collect the value, and download its checklist. A family already on file is
skipped rather than updated by the spreadsheet, so edit existing records in the
application when the review says their details differ.

## Resolve duplicate rows without losing the review trail

`Duplicate Row` is reserved for a deterministic copy, not two people who merely
share a name. The active rows must match on QR, relationship, normalized name,
suffix, parsed birthday, household address, and barangay. A blank identity
field means the server cannot prove a duplicate, so correct that field through
the normal editor first.

When review identifies a duplicate group, open its resolver and choose the one
complete row to keep. The resolver compares the candidate rows side by side for
two rows, or in a selectable grid for larger groups. It never merges two rows
into a hybrid record.

The row you keep stays **active**. Every other row in that duplicate group is
**discarded** from this import:

- In All, discarded rows remain visible in a muted state with, for example,
  `Discarded as duplicate of row 589`.
- The Discarded filter shows only those rows. They offer Restore instead of
  Edit.
- Discarded rows do not take part in family building or persistence, but stay
  in staging and the review change log until you Confirm or Cancel.
- Restore makes the rows active again and revalidates them. If the duplicate
  group returns, it is Must fix again and Confirm remains disabled until you
  resolve it.

This reversible decision is review-only state, implemented by
`app/Libraries/ImportReviewResolution.php`. It lets you remove a confirmed
copy without deleting the survey evidence or silently losing a row.

## Three repeated-QR outcomes

A repeated QR is normal for members of one family. These three cases look
similar in Excel but require different actions:

| Review label | What it means | Result |
|---|---|---|
| `Duplicate Row` | The rows are provably the same person and household record. | Must fix. Keep one row in the resolver and discard only its copies. |
| `Multiple Heads (Same Family)` | One contiguous QR block contains two or more Head rows. | Must fix. Correct the relationship values. Do not use the duplicate resolver. |
| `Duplicate QR (Multiple Families)` | Separate populated QR blocks each have a Head, and the Heads are different people. | Must fix. Correct the second household's QR. The review names both row ranges and heads, and offers no discard action. |
| `Family rows not together` | A separated continuation does not prove a different family, such as a later block with the same Head. | Warning only. It imports, but check the sorting or paste order. |

For example, rows 3 to 5 for QR 6001 with Juan as Head, followed later by rows
20 to 22 for QR 6001 with Pedro as Head, are `Duplicate QR (Multiple Families)`.
Correct Pedro's household QR. Two Head rows together in rows 3 and 4 are instead
`Multiple Heads (Same Family)`. A later continuation of Juan's family is only
`Family rows not together` when it does not prove a second household.

## Diagnostic tool

Run the real parser and validator from the repository root when you need to
inspect a workbook without uploading it:

```bash
php tools/validate-import.php path/to/workbook.xlsx
```

The tool reports row, family, member, blocking, and warning counts plus
representative messages. It needs database access because QR ownership and
current sectors, services, income labels, and barangays are database-backed.
It is a diagnostic view of the same rules in
`app/Libraries/FamilyExcelImporter.php`, not a substitute for review.

## The code

| Class or file | Responsibility |
|---|---|
| `app/Controllers/Families/FamilyImportController.php` | template download, upload, review actions, staged Apply, duplicate resolution, restore, Confirm, and Cancel |
| `app/Libraries/FamilyExcelTemplate.php` | generates the Ver4 workbook, Reference sheet, and Excel-only `CHECK` preflight |
| `app/Libraries/FamilyExcelImporter.php` | parses, canonicalizes, validates, classifies QR and row duplicates, and builds active families |
| `app/Libraries/ImportStagingStore.php` | holds staged rows, errors, discarded state, duplicate groups, and change log between upload and Confirm |
| `app/Libraries/ImportReviewResolution.php` | applies keep, discard, restore, and active-row rules without writing family records |
| `app/Libraries/ImportReviewQuery.php` and `app/Libraries/ImportReviewPresenter.php` | provide review filters, row shapes, labels, resolver data, and discarded-row presentation |
| `app/Jobs/FamilyImportJob.php` | runs the queued import parse and later persists only active rows after Confirm |
